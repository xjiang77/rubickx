# eli5-rubickx

以 [dreambigou/eli5](https://github.com/dreambigou/eli5)（本仓库收录于 `../eli5/`，MIT）为基底，在它之上加 Rubickx 的页面合同。合同写在仓库里，`scripts/check_eli5.py` 才有据可查。

## 读者与讲法

按 eli5 skill 的受众分档，本页面的读者取 **Engineer / College Student**：具备工程或大学理工基础，但对这个主题没有背景。对这一档，eli5 的要求是：使用规范术语（省略术语反而显得居高临下），给出理论并配实际应用，重点讲取舍、边界与设计决策，表述简洁。

eli5 的四步结构对应到页面上：

| eli5 结构 | 页面位置 |
|---|---|
| Start with the "what"：一句话抓住本质 | 「定义与示例」的首句定义 |
| Use an analogy：接上读者已知的事物 | 「定义与示例」的实际应用示例（优先用常见、可验证的应用，而不是比喻） |
| Fill in details：按读者水平逐层展开 | 「逐步推演」3–6 屏 |
| End with the "so what"：对读者有什么用 | 「工程应用」与「知识树」 |

eli5 另有两条要求同样适用：先讲目的，再讲机制；宁可讲清 80% 的核心，也不追求面面俱到而让读者跟不上。

## 知识说明的专业文体

**定义**：知识说明的专业文体，是以陈述方式准确说明概念的定义、条件、机制与结论的书面文体。它面向上述读者，使用学科通用术语，依靠结构（定义、编号步骤、公式、图）而不是口语、设问和语气引导阅读。它是 dragon-vault `99_System/Specs/02_Chinese_Style_Spec.md` 在知识说明场景下的具体化，两者冲突时以 Spec 为准。

**规则**：

1. **标题用名词性短语**，标明内容类别或概念名，不用问句和口语短语。固定标题见下方「页面结构」。标题只写实际有的内容：只交代背景就写「背景」，另有需要单独说明的采用理由时才写「背景与动机」。
2. **定义用"属 + 种差"**：先说它属于哪一类（算法、方法、判断框架……），再说与同类的区别。定义之后紧跟一个常见、易懂、可核对数值的实际应用示例。
3. **先例子，后公式**。机制先用具体例子按编号步骤讲，每步写"步骤名：动作 + 对象 + 结果"，用日常语言和带单位的数值；步骤里可以写文字公式（如"loss =（预测用时 − 实际用时）²"），不写符号公式。一个量在给出数值之前，先给出它的计算公式，例如先写 loss function 的形式，再写 loss 的值。例子讲完后单列公式：先写完整的一般公式（例如 loss function 写成 L = (ŷ − y)² = (w·x − y)²，不只写 L = e²），最后代入本例数值。示例选用自然单位下数值就简单的场景，避免为凑整数改换单位（如把房价换算成"百万元"），否则读者难以理解 loss 的量级。讲优化过程的 topic，例子末尾用一张表列出几轮迭代（参数、预测、loss、gradient），让读者看到 loss 逐轮下降。
4. **用术语，不用口语替代**：不用"放大倍数"代替 local derivative，不用"往回走"代替"沿 computational graph 反向计算"。
5. **陈述客观**：不用第二人称和语气词（吧、呢、啦），不用口头程度词（特别、超级、一下子）；因果关系写明依据（因此、由于）。
6. **比较要量化**：写出对象和尺度，例如"计算量与一次 forward pass 同一量级"，不写"快得多"。
7. **结论与依据相称**：正文未核验的判断，写成"通常""一般"并收窄范围，不写成定论。

**示例**（口语 → 专业）：

| 口语化写法 | 知识说明的写法 |
|---|---|
| 为什么要懂它 | 背景（另有采用理由时写「背景与动机」） |
| 它是什么 | 定义与示例 |
| 从哪里来 | 起源与发展 |
| 用一个例子推演一遍 | 逐步推演 |
| 去试试 / 想深入 | 实践 / 参考资料 |
| 看一个只有一个 parameter 的预测模型…… | 以外卖配送用时预测为例：模型根据配送距离估算送达用时，唯一的 parameter 是每公里用时。 |
| 距离 x = 2（公里），w = 3（分钟／公里），预测 ŷ = w·x = 6（分钟），L = e² = 16 | 示例：一单配送距离 2 公里，每公里用时估计为 3 分钟，预测送达用时 6 分钟；loss =（预测用时 − 实际用时）²，为 16。公式：L = (w·x − y)²；代入 x = 2，w = 3，y = 10，得 L = 16。 |
| 从 L 出发往回走，每经过一步就乘上这一步的 derivative | 从 L 出发沿 computational graph 反向计算，每经过一个运算，乘以该运算的 local derivative。 |
| 这三样懂了，backpropagation 就只剩按顺序计算 | 掌握这三个概念后，backpropagation 可归结为按依赖顺序执行的乘法与加法。 |
| 只保留一条，结果就错了 | 若只计入其中一条路径，所得 gradient 不正确。 |
| 答错了类别，后面的计划会一路偏离 | 类别判断错误会使后续的排期与投入估计产生系统性偏差。 |

**术语**：专业术语用英文原词，第一次出现时在括号里给常用中文译名，之后只用英文，例如 loss function（损失函数）、gradient（梯度）、learning rate（学习率）、computational graph（计算图）。句首的英文术语首字母大写。日常词语（面积、房价、误差）用中文。同一概念全文称谓一致；页面用词跟随知识库正文，例如可行性三类用正文的"不可能 / 代价问题 / 可靠性问题"。英文术语在中文句子里用原形（单数），数量由中文表达，例如"全部 parameter""1750 亿个 parameter"，不写 parameters：中文名词不区分单复数，同一术语保持一种写法也便于检索和校对。

**联系 AI 工程**：用简单示例讲机制之后，写出它与 LLM 等真实系统的对应关系（例如表格"对应到 LLM 训练"：输入、parameter 的规模、预测、loss function、gradient 分别对应什么），让读者把示例迁移到实际工作中。

## 输入

一个 topic id（如 `1.6.1`）。从 `web/topics.json` 读出：能力、标题、`knowledge.notes`（私有知识库 dragon-vault 里的正文路径）、`practice`。

## 页面结构

从上到下：标题与一句话导语 → 概述 → 逐步推演 → 固定结尾。标题写"概念名（中文译名）：它解决的问题"，不用悬念式标题。

1. **读正文**。打开 `knowledge.notes` 里的每一篇（在 dragon-vault 中）。机制与判断只从正文取，不另加正文里没有的结论。正文未核验时，页面顶部加 `<p class="flag">`。
2. **概述**（`<p class="part">概述</p>`，三块缺一不可，段落与步骤合计不超过 600 个汉字）：
   - `.ctx.why`「背景」：它解决的问题，以及缺少它时工程上的具体障碍；另有需要单独说明的采用理由时，标题写「背景与动机」；
   - `.ctx.what`「定义与示例」：首句给出定义（规则 2）并引出一个常见的实际应用示例；随后依次是 `<h3>示例</h3>` 与 `<ol class="steps">`（日常语言与数值，不写符号公式；优化类 topic 末尾加迭代表 `.rounds`）、`<h3>公式</h3>` 与 `.formula`（每行一个 `.fl`，先一般公式，后代入数值；单位换算只在这里说明一次），最后配图（规则 3）。示例里每个变量都有实际含义和单位（如面积、单价、房价）；后面的推演沿用同一个示例；
   - `.ctx.origin`「起源与发展」：提出者、年份与演进，能画成时间线就画。正文没有写历史时，可以用公开来源补，来源列在「参考资料」里，并在知识库正文补上对应一节。
3. **逐步推演**（`<p class="part">逐步推演</p>`，3–6 屏）。先用 `.intro` 说明示例与真实情况的关系，并以"本例说明以下要点："列出 2–3 条要点，后面每一屏都服务于其中一条。涉及计算或机制的 topic，每屏给出公式（`.formula`），数值可以逐步核对，能做数值验证的写出验证。每屏一张内联 SVG 主图，配一两句话；图里的每个元素都有标注。所有屏的说明文字合计不超过 400 个汉字。
4. **画图**。
   - 复制 `web/learn/_template.html`，**不要改 `<style id="eli5-base">`**，检查脚本会逐字比对。`body` 的 class 按 pillar 取 `ai` / `se` / `agents` / `build`。
   - 用模板里的 SVG 类：`box`、`hl`、`op`、`fwd`、`bwd`、`faint`、`t`、`tb`、`tc`、`ts`。箭头 marker 放在页首隐藏的 `<svg><defs>` 里，填色写 pillar 色的字面值。
   - 每张 SVG 带 `role="img"` 与说清画面内容的 `aria-label`。
   - 手机上 800 宽的 viewBox 大约缩到 0.44 倍：图内文字至少用 `ts`（22），能放进段落的解释就不写在图里。按内容裁 viewBox，不留大片空白。
   - 不用 emoji、外部字体、外部脚本或图片。
   - 前置概念第一次出现时，用 `<a class="term">` 链接到对应图解页的锚点（例如 `math-prerequisites.html#chain-rule`）。
5. **固定结尾**，按顺序六块：
   - `.limits`「适用条件与局限」：本例不能说明的内容，结论不成立的条件；
   - `.uses`「工程应用」：3–4 个真实场景，每个写清如何用这个概念做出判断（例如 loss 变成 NaN 时先检查什么）；
   - `.summary`：一句话总结；
   - `.tree`「知识树」：前置知识、核心概念、延伸主题、应用场景四个方向，按 `web/topics.json` 的 `relations` 与知识库正文的「知识树」一节填写；有 ELI5 页的链接过去，没有的写 topic 编号并标"图解待写"；
   - `.try`「实践」：实践路径与命令；实践待建时写"实践待建"和计划；
   - `.deeper`「参考资料」：正文标题（知识库不公开，只写标题，不放链接）和公开来源链接。
6. **元数据**：`rubickx-topic`；`rubickx-derived-from` 写成"正文路径@正文 frontmatter 的 updated"，供知识库侧检查页面是否过期。
7. **登记**：文件放在 `web/learn/<capability-id>/<slug>.html`；在 `web/topics.json` 的该 topic 下写 `eli5: {path, derived_from: {note, updated}}`。
8. **检查**：`python3 scripts/check_eli5.py && python3 scripts/check_topics.py && python3 scripts/render_skills_map.py --check`。再在 1280 宽和 390 宽下各截一张图看一遍：无横向滚动，图内文字能读。

## 不能做的事

- **不给练习答案**。实践是本人手写的练习时（例如 nanochat 的 C5 约束），页面只讲直觉和练习入口，不贴实现代码。
- **不越过公开边界**。页面随 GitHub Pages 公开：不写个人项目的内部事实、内部数字或私有链接；拿不准时先问。
- **不替正文下结论**。正文标为"未验证"的判断，页面也不能说成定论。
